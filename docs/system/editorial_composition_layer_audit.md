# Editorial Composition Layer Audit

Date: 2026-04-24  
Scope: backend + mobile read-only audit before any new `Editorial Projection Composer` work.  
Constraint respected: no code changes.

## Executive Take

The repo already contains multiple live editorial composition layers.  
For `profile_narrative_projection_v1`, the safest strategy is **reuse selective existing composition utilities** instead of creating a brand-new composer stack.

## 2) Which modules generate long-form narrative pacing

Primary long-form pacing is generated by:

1. `profile_narrative_engine_signature.py`  
   - Mode/family pacing per block (`direct/observational/cinematic/intimate`) via `select_rhythm_family()` and `render_block_template()`.
   - Balancing and anti-repetition routines (`_choose_distinct_copy`, `_append_balance_to_body`, opening/body uniqueness).

2. `phrase_lib_tr_profile.py`  
   - Multi-template body render (`_BODY_TEMPLATE_BY_MODE`), teaser/micro editorialization, and quality-driven candidate selection.

3. `profile_detail_editorial.py`  
   - Multi-paragraph scaffolding for deep reading (`_build_thread_editorial_scaffold`, family-origin/tension/strength/growth lines).

4. `narrative_renderer_v26.py` (core story, not profile cards)  
   - Multi-paragraph synthesis across slots and sections with connector budgets and fallbacks.

## 3) Which modules combine multiple meaning parts into cards/sections

Most important combiners:

1. `public_builder._build_profile_narrative_v3()`  
   - Combines `profile_narrative blocks + narrative_v2 bundles + supporting_threads + personality_imprint`.
   - Produces `core_blocks`, `extra_blocks`, `detail_cards`.

2. `profile_v8_payload_builder.build_fragment_pool()` + selection functions  
   - Combines `profile_narrative`, `sections_v2`, `supporting_threads`, `narrative_v2`, `personality_imprint`, chart anchors/rules.
   - Produces `profile_v8` and `full_map_v8` via ranking/dedupe/caps.

3. `supporting_threads_builder.build_supporting_threads()`  
   - Converts section-level cards into thread-level payload.

4. `home_orchestrator._assemble_deep_payload()`  
   - Combines natal/transit/sky outputs into home-deep sections and hooks.

## 4) Mislocated or misnamed “engine” modules that are actually composition layers

Proven cases:

1. `profile_narrative_engine_signature.py`  
   - Named as engine; operationally a **renderer/composer** with copy templates and editorial quality controls.

2. `profile_narrative_engine.py`  
   - Named as engine; operationally a **runtime orchestrator/wrapper** (engine selection, rollout, shadow debug diff, telemetry).

3. `profile_narrative_engine_legacy.py`  
   - Named as engine; operationally **static template renderer** for legacy fallback payload.

4. `composite_meaning_engine.py` (`CompositeMeaningEngineV1`)  
   - Named as engine; operationally **template mapper + ranker (top-2 selection)**, not a deep generative engine.

Non-issue (name aligns reasonably):

- `upper_meaning_engine.py` behaves like a rule-matching selector and is appropriately engine-like.

Mislocated composition logic (not naming, placement concern):

- `public_builder.py` currently hosts `_build_profile_narrative_v3()` which is a substantial composition layer inside a public serializer module.

## 5) Can `profile_narrative_projection_v1` reuse existing modules?

Short answer: **Yes, partially; with constraints.**

### Reusable now (low risk)

1. `profile_detail_editorial.py`  
   - Reuse to enrich projection detail blocks from node summaries/evidence while preserving editorial depth.

2. `editorial_render_policy.py`  
   - Reuse `apply_phrase_policy` and rhythm helpers for teaser/micro polishing and consistency checks.

### Reusable with adapter (medium risk)

1. `profile_v8_payload_builder` selection logic  
   - Potential reuse if meaning_graph nodes are adapted to `NarrativeFragment` shape.
   - This gives existing ranking/dedupe/section caps without inventing new math.

### Not directly reusable for graph-only projection (high coupling)

1. `profile_narrative_engine_signature.py`  
   - Depends on `chart + natal_graph + primitives + signatures`; not graph-only.
2. `supporting_threads_builder.py`  
   - Also chart/natal_graph-driven and legacy-source coupled.

Critical constraint:

- `profile_narrative_projection_v1` rule says “derive only from `meaning_graph_v1_1`”.  
  So reuse must be limited to utilities that do not re-import legacy semantic sources.

## 6) What should be reused, moved, renamed, or left alone

| Item | Recommendation | Why |
|---|---|---|
| `profile_detail_editorial.py` | Reuse | Best existing deep editorial scaffolding; low coupling if fed normalized projection blocks. |
| `editorial_render_policy.py` | Reuse | Already canonical for rhythm/phrase quality discipline. |
| `profile_v8_payload_builder` scoring/selection | Reuse later via adapter | Proven ranking/cap/dedupe behavior; avoid re-implementing selection rules. |
| `_build_profile_narrative_v3` in `public_builder.py` | Move later (not now) | Real composition logic is buried in serializer layer; technical debt but currently live. |
| `profile_narrative_engine_signature.py` naming | Rename later to composer-oriented name | Behavior is composition/rendering more than pure engine. |
| `profile_narrative_engine.py` naming | Rename later to orchestrator/dispatcher | It chooses engine/migration/debug mode, not text generation itself. |
| `profile_narrative_engine_legacy.py` | Leave for now | Still wrapped for debug/rollout paths; removal needs telemetry gates. |
| `UpperMeaningEngine`, `CompositeMeaningEngineV1` | Leave | Upstream semantic selectors; not projection-composer targets right now. |
| Transit composer/assembler modules | Leave | Separate surface/problem domain; avoid cross-domain coupling. |

## 7) Safest next implementation step

Safest path before introducing any new composer:

1. Keep `profile_narrative_projection_v1` as graph-only source.
2. Add a tiny adapter in projection layer: `MeaningNode -> profile-like block` (headline/teaser/body/chips/family).
3. Reuse `build_editorial_detail_blocks_for_profile_block()` (and optionally thread-style scaffolding for evidence-derived lines) to increase editorial depth.
4. Reuse minimal `editorial_render_policy` helpers for text polish/consistency.
5. Do **not** call `profile_narrative_engine_signature` or `supporting_threads_builder` from projection path.
6. Add parity-focused tests measuring:
   - detail-block richness,
   - repetition/quality issue counts,
   - traceability preservation (`node_id`, `evidence_id`).

This gives immediate editorial uplift with minimal architecture risk and without violating graph-only derivation.
